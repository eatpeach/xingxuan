## 背景

商机详情 →「对客报价」步骤 → 点「生成对客报价」，会**无条件删掉该商机下所有旧报价**，
而 `orders.quote_id` 是 `ON DELETE CASCADE`，级联链是：

```
customer_quotes → orders → contracts / payments / commissions
                            合同      收款       返佣
```

**`payments` 是收款记录，`commissions` 是返佣。销售重新生成一次报价，已成交订单的收款流水和返佣直接消失，不可逆。**

### 已核实的四条事实

| # | 位置 | 事实 |
|---|---|---|
| ① | `backend/api/handlers/customer_quote.php:750` | `DELETE FROM customer_quotes WHERE inquiry_id = ?` —— **无条件**，不看有没有订单、有没有开票 |
| ② | `backend/config/database.php:268` | `orders.quote_id` → `customer_quotes(id) ON DELETE CASCADE` |
| ③ | `backend/config/database.php:285/300/317` | `contracts` / `payments` / `commissions` 三张表 → `orders(id) ON DELETE CASCADE` |
| ④ | `frontend/src/pages/InquiryCompare.tsx` | **`Popconfirm` / `Modal.confirm` 数量 = 0**，没有任何二次确认 |

④ 最致命：唯一的"提示"是**删完之后**弹的绿色成功消息
（`InquiryCompare.tsx:223`：`已生成 XXX，已覆盖旧报价 BJ2026xxxx`）——
**事后通知，而且是绿色的成功态**，销售根本不会意识到刚删了收款记录。

代码注释写「按产品要求即为预期行为」。但那条"产品要求"说的是
「一个商机只保留一份对客报价」，**不等于"可以删掉已收的钱"**。

## 决策（CTO，2026-08-08）

**分两层处理，后端硬拦为主、前端确认为辅。**

### 第一层：有订单或已开票的 → 后端硬拦，不给确认选项

`buildCustomerQuote` 在删除前先查：该商机下的旧报价里，
**只要有任何一条已生成订单（`orders` 有记录）或已开票（`invoice_no` 非空）**，
直接 `jsonError` 拒绝，**不删任何东西**。

错误信息要写清楚拦的是什么、让人知道下一步怎么办，例如：

> 报价 BJ20260808001 已生成订单 DD20260808001（含收款 2 笔），不能覆盖。
> 需要改报价请先作废该订单，或新建商机。

**为什么是硬拦不是强确认**：删掉已收款记录是不可逆的资金数据丢失，
任何"你确定吗"都不该能越过。销售在赶单子的时候，弹窗一律点确定——这是人性，不是纪律问题。

### 第二层：没有订单的 → 允许覆盖，但要前端二次确认

纯草稿报价（无订单、未开票）覆盖掉没有资金后果，保留现在的便利。
但要加 `Popconfirm`，**列出将被删除的报价单号**，不能再是事后绿字。

## 执行步骤

- [ ] **1. 后端加拦截**（`customer_quote.php` 的 `buildCustomerQuote`）
      - 删除前查旧报价是否有关联 `orders` 记录、或 `invoice_no` 非空
      - 命中则 `jsonError` 拒绝，**在任何删除动作之前返回**，不要先删再回滚
      - 错误信息带上：报价单号、订单号、该订单已收款笔数
- [ ] **2. 后端返回"将被覆盖的报价"预检信息**，供前端做确认弹窗
      （可复用现有 `replaced` 字段的思路，或加一个 `previewOverwrite` 分支——你定，别过度设计）
- [ ] **3. 前端加二次确认**（`InquiryCompare.tsx`）
      - 生成前 `Popconfirm`/`Modal.confirm`，**列出将被删除的报价单号**
      - 后端拒绝时把错误信息**显示出来**——注意本项目的老毛病：
        `api.post` 没 try/catch 会静默无反应（02 号单踩过同一个坑）
- [ ] **4. 盘一下历史上有没有已经发生过**
      - 查 `op_logs` 里 `buildCustomerQuote` 相关记录，对照 `orders` 表看有没有断档
      - 查线上现有商机中，有多少处于「已有订单 + 还能被重新生成」的危险状态
      - **这一步是只读**，出个数字给 CTO，不要动数据

## 🔴 红线

- **拒绝路径必须零副作用**：先查后删，不要"先删了再判断要不要回滚"
- **不碰存量数据**。本单只改代码 + 只读盘点，任何数据修复另开单
- 动了 `frontend/` 就必须 `npm run build` 并把 dist 一起提交
- 改完 commit + push，**不要自己去服务器 `git pull`**，部署由用户在宝塔做
