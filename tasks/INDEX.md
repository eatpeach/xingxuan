### 1. 🔴 生产的 `php.ini` 上传上限是多少？（运维配置，开发改不了）

14 号单给附件上传加了 20MB 限制，**但这个数可能根本达不到**。
本机实测 `post_max_size=8M` / `upload_max_filesize=2M` ——
**超过 `post_max_size` 的请求在进入 PHP 代码之前就被拒了**（`$_FILES` 是空的，代码里的检查压根跑不到）。

实际上限 = `min(post_max_size, upload_max_filesize, 20MB)`。

**如果生产也是 2M，「图纸类 PDF 常见 5~15MB」就传不上去** ——
等 14 的入口做出来，会立刻表现为「大图纸传不了」，而且报错来自 PHP 不是业务代码，不好排查。

## 📌 方法论：改验收判据必须自证没有粉饰（开发人员B 2026-08-10 提出，CTO 采纳为通用纪律）

**问题**：中途修改验收判据，最容易被质疑的是「**是不是改了个能过的标准**」。
判据是自己定的、结果是自己量的，光说「新判据更合理」没有说服力。

**纪律**：凡是改验收判据，**必须给出「用新尺子去量改动前的状态，结论与旧尺子一致」的证据**。

**范例**（07 号单，B 做的）：把「快照完整」的判据从 `invoice_entity_id IS NOT NULL`
换成 `IFNULL(invoice_entity_name,'') <> ''` 时，他验证了——
**回填前**用新判据算出来同样是 **0**，与旧判据结论一致；两把尺子**只在回填后分歧**，
而那正是旧尺子错的地方。

→ 新判据没有把回填前的问题粉饰掉，它只是不再把「按设计留空的 `entity_id`」当成缺陷。

**做不到这条自证的判据变更，一律先报 CTO，不要自己改。**

## 📌 纪律：重建 `dist` 后必须做回归检查（开发人员B 的做法，CTO 采纳）

A、B **共用同一个工作区**（不是各自 clone），而 `frontend/dist` 进 git。
所以任何一次 `npm run build` 都可能**把别人的半成品打进包**，或**把已上线的东西打掉**。

**纪律**：每次重建 dist 后，在提交前确认已上线的功能仍在新包里。B 的做法（照抄即可）：

```bash
git status                     # 先看清哪些文件不是自己的
grep -c "q-sign" frontend/dist/assets/index-*.js          # 04：应为 0
grep -c "previewQuoteOverwrite" frontend/dist/assets/index-*.js   # 05：应 >0
grep -c "请先选择收款主体" frontend/dist/assets/index-*.js          # 06：应 >0
```

**只 `git add` 自己改的文件，禁止 `git add -A`。**

（另：若改动只涉及注释/文档，minify 后产物字节可能一致，`git diff` 会显示 dist 无变化——
这种情况不必重跑回归检查，但要确认 `git diff` 确实是空的。）

## 📌 方法论三条（2026-08-10 新增，都是被开发纠正出来的）

### 1. 验 `.gitignore` 必须造真文件跑 `git add -A --dry-run`，**不能用 `git check-ignore`**

CTO 在 20 号单里规定用 `git check-ignore` 自证，**这个方法是错的**，B 指出并纠正。
CTO 随后亲手复现了两个坑：

| 坑 | 实证 |
|---|---|
| **默认跳过已追踪文件** | `backend/storage/brand/channels.png`（已追踪）：`check-ignore` 说「不忽略」，`--no-index` 说「规则会命中」 |
| **`-q` 退出码 0 = 匹配到某条规则，不等于「被忽略」** | `data/.gitkeep` 退出码 0，但 `-v` 显示命中的是 `!data/.gitkeep`——**取反规则，实际是放行** |

**后果**：CTO 原本规定的「逐个过已追踪文件、没命中就算通过」，
**是一个永远会通过的检查**——对任何 `.gitignore` 都成立，包括一个把所有东西都忽略掉的。

**正确做法**：**造真文件，跑 `git add -A --dry-run`，看它会不会被 staged。**
这正是要防的真实场景（一次手滑）。要看规则细节时用 `git check-ignore -v`（看命中哪条），
**不要只看 `-q` 的退出码**。

### 2. 「有备份所以可回滚」——**还原路径必须被实际验证过一次**

从 01 号单起，每张涉及生产写操作的单子都写着「`--apply` 前自动备份」。
**但直到 2026-08-10 B 在本地实跑之前，没有任何人验证过那个备份还原出来是不是能用。**

它一直只是**脚本里的一句承诺**。B 对 `backfill_invoice_snapshots.php` 和
`purge_all_products.php`（**删全表脚本，已在生产跑过**）各做了一次真实还原，
两个都精确还原成功。

**纪律**：方案里写「有备份可回滚」的，**必须有一次实际的还原验证**，
否则「有备份」只是安慰。**尤其是删除类脚本。**

### 3. 单子的前提由 CTO 写，**CTO 会写错——执行前先验证前提**

截至 2026-08-10，CTO 已被开发纠正 **5 次**，全部是「看了文档 / 看了一行代码就下结论」：

| # | CTO 的错误前提 | 谁纠正 |
|---|---|---|
| 1 | 「文档写着（用户已改）」→ 判定 `admin123` 是失效口令 | A（它是 `seed()` 里的活代码） |
| 2 | 07 的验收判据要求 `entity_id NOT NULL`，与自己的裁决直接矛盾 | B |
| 3 | 12 号单假定 `status` 只有 `draft`/`sent` 两个值 | B（实际四个，`confirmed` 在印英文） |
| 4 | 13 号单假定 `DISPATCH_STATUS` 缺 `void` 标签 | B（方向反了，是派单列表挂了报价的词汇表，100% 的行印英文） |
| 5 | 20 号单规定用 `check-ignore` 自证 | B（该方法对已追踪文件永远返回"不忽略"） |

**所以：接单后第一件事是核实单子的前提，核不对就停下来报，不要照着错的前提往下写。**
这条已被 07 / 12 / 13 / 20 四次证明有效。
