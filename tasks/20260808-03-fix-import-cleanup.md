## 背景

[20260808-01](20260808-01-purge-product-library.md) 已定位事故根因，本单是那张单「后续待办」的第一条。
**顺序：先跑完 01（清空），再做本单，最后才重导。** 本单不做重导。

### 已核实的缺陷

`scripts/data-fixes/import_ikad_products.php:99` 与 `:105`：

```php
"... WHERE supplier_id = ? AND name IN ({$ph}) AND base_price = 0 AND status = 'pending'"
```

清理条件要求 `status = 'pending'`，但那批旧商品当时**已被置为 `status = 'on'`**，条件不命中 →
旧的按尺寸拆分数据留下来，合并版（`status='pending'`，第 165 行插入）顶不上去，
于是货架上展示的一直是旧的错数据。

**已核实、不用再查的两点**（省得你重复排查）：

- `$oldNames` 取自 `$items`，即 `ikad_products.json` 的 **48 条尺寸码原始清单**
  （`DX MINIMALIST Series` / `DT MOZAIC Series` 这种），**名字是对得上旧数据的**
- 旧数据 `base_price` 确实为 0

> 所以**缺陷只在 `status` 这一处**，`name` 和 `base_price` 两个条件都没问题。别顺手一起改。

## 目标

让清理步骤**不再因为「旧数据被人动过状态」而静默失效**，并且失效时能被发现。

## 重导为什么不在本单（决策留痕）

重新导入 IKAD 商品（按花色合并成 7 个产品）**卡在两件事上，都不是技术问题**：

1. **价格没有** —— 01 号单已确认 25 条全是 `base_price = 0`。没有价格就重导，等于把同一个事故再演一遍
2. **[20260808-02](20260808-02-price-gate-before-onshelf.md) 的上架闸门要先上** —— 否则重导后仍可能被误上架成 0 价

**价格到位 + 02 上线 = 重导开单。** 两个条件缺一个都不开。
