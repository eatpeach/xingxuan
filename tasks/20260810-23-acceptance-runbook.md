产出：`tasks/PRODUCTION-ACCEPTANCE-RUNBOOK.md`（名字你定）。

## 要点

### 1. 按「测试数据生命周期」编排，不按单号编排

十张单里好几张要造同一批东西。**把它们串成一条链**，一次造、多处用、最后一次清干净。

大致形状（你按实际依赖重排）：

```
建 0 价测试商品（02）→ 补价上架（02）→ 货架确认（02）
  → 建测试商机 → 生成对客报价（12）
  → 派单 + 供应商报价 → 采纳/作废（13）
  → 标记成交出订单（05 的前置）→ 重新生成报价应被拒（05）
  → 开票选主体账户（06）→ 发票打印页确认（06）
  → 标记已收款 / 逾期看板（11）
  → 清理
```

**这样比十张单各造各的省一大截，也不容易漏清理。**

### 2. 每一步写清「点哪里 / 应该看到什么」

不要写「验证 02 的闸门」。要写：

> 商品库管理 → 新建商品，价格填 0 → 点「审核通过」
> **应弹**：「商品未定价（底价为 0），不能上架」
> **且**：状态仍是 `pending`（没有被改成 `on`）

**执行的人可能是老板本人，他不需要理解背景就能照着做。**

### 3. 🔴 07 的发票打印页抽查排在最前面

那是回填的**全部意义**——**渲染变了就要回滚**，越早知道越好。

其余九张都是「新功能好不好使」，**只有这一条是「有没有把已经在用的东西弄坏」**。
性质不同，优先级也不同。

具体：打开 `INV20260804001`（李总那张）的发票打印页，
**抬头、银行信息必须和回填前一模一样**。

### 4. 标出哪些必须用测试数据、哪些绝对不能碰

线上有 **12 条已成单商机、已收 Rp 3,504,495,889、9 条返佣、21 张历史发票**。

**清单里要显式点名"不要碰这些"，别指望执行的人记得。**
尤其 05 的验收要造「有订单+有收款」的场景——**必须是新造的测试商机，不能拿真实的试。**

### 5. 最后一段：清理清单

造了什么就列什么，**逐条打勾删掉**。

测试数据留在库里会污染以后的盘点——**07 的盘点脚本会把测试发票算进空快照统计**，
02 的货架会显示测试商品。

### 6. 标注哪些步骤要查库，命令写好能直接贴

有几条验收得 `sqlite3` 查，比如 08 的：

```bash
sqlite3 /www/wwwroot/www.xingxuan.cc/backend/data/xingxuan.db \
  "SELECT no, invoice_no, invoice_entity_name, invoice_bank_account_no
   FROM customer_quotes WHERE invoice_no != '' ORDER BY id DESC LIMIT 3;"
```

### 7. 10 号单单独提醒一条

10 改的是 `seed()`，**它在鉴权之前、每个请求都跑**。
它的验收不是"点某个功能"，是：

- 访问首页确认无 500（**已部署时做过，200**）
- 确认 `users` 表账号一个没变、没新增
- 确认 `system_settings` 的 `bank_*` 现有值没被清空

**这几条现在就能查（不需要登录态）**，可以单独列一节标「无需开门即可完成」。

## 🔴 一条硬要求

**你不能自己跑这些验收**（要登录态），所以**清单必须写到「另一个人照着能执行」的程度**。

写完自己过一遍：**假设执行的人完全不知道这十张单的背景，他能不能一路走下来？**
卡住的地方就是写得不够的地方。
